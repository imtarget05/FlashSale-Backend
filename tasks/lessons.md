# Lessons Learned

## Phase 1: Naive Synchronous API
- **Functional testing under single-request load masks race conditions**: Single-request happy-path tests pass completely, creating a false sense of reliability. Under sequential traffic, the basic read-check-write pattern (`SELECT AvailableStock` followed by `UPDATE`) behaves as expected, but this pattern provides zero safety under concurrent access.
- **Intentional naive baseline establishes measurable reference**: Intentionally building the naive architecture first (Client → Order API → PostgreSQL) provides an empirical baseline for latency, resource usage, and error characteristics. Architectural complexity should never be introduced before baseline failure modes are measured.
- **Minimal surface area clarifies domain behavior**: Keeping initial compute and persistence in a single synchronous path isolates business domain logic from distributed infrastructure concerns, making baseline performance and failure points easy to trace and analyze.

## Phase 2: Concurrency Testing
- **Bugs must be evidence-backed failures, not theoretical assumptions (ADR-001)**: Never introduce locks, caching layers, or message queues "just in case." Build an automated, reproducible concurrency test harness (`load-tests/concurrency/oversell_demo.py`) that audits database state against an inventory conservation invariant: `final_stock == initial_stock - accepted_units`.
- **Reproduced 5x overselling under default isolation**: A burst of 50 simultaneous purchase requests competing for 10 available units resulted in 50 accepted orders (50× 200 OK) while available stock only decremented from 10 to 9. Under PostgreSQL's default `READ COMMITTED` isolation level, concurrent transactions read identical initial stock snapshots before any transaction commits its decrement, resulting in silent lost updates.
- **Automated harness over manual verification**: Concurrency anomalies cannot be detected or diagnosed through manual API calls or isolated unit tests. Automated execution with precise timing and assertion of final state is required to definitively expose race conditions.

## Phase 3: Database-Level Concurrency Control
- **Atomic conditional UPDATE provides row-level compare-and-set (ADR-002)**: Wrapping `UPDATE "Products" SET "AvailableStock" = "AvailableStock" - @quantity WHERE "Id" = @productId AND "AvailableStock" >= @quantity` in an explicit database transaction with order insertion guarantees inventory consistency at the database engine level. The number of affected rows (1 for success, 0 for out of stock) definitively decides order acceptance or rollback.
- **Zero overselling invariant mathematically verified**: Tested with the identical 50-buyer concurrency harness: exactly 10 requests were accepted, 40 requests received `409 Conflict`, and final database stock was exactly 0.
- **Application-level locks fail under horizontal scaling**: Process-level locking mechanisms (such as C# `lock` or `SemaphoreSlim`) are architectural dead-ends for multi-instance deployments; they fail the moment the API scales beyond a single container replica.
- **Avoiding serialization failure retry storms**: While `SERIALIZABLE` transaction isolation prevents lost updates, it triggers transaction serialization aborts and retry storms under high contention. Atomic conditional updates hold row locks for only microseconds without retry complexity.

## Phase 4: High-Load Bottleneck Analysis
- **Correctness does not equal scalability under extreme load**: Stress testing the atomic conditional update with 200 concurrent buyers for 20 units preserved zero overselling, but p95 latency degraded super-linearly from 245 ms to 574 ms due to lock queuing on the contested product row.
- **The Hopeless Buyer Problem**: 90% of requests (180 out of 200) consumed network bandwidth and scarce database connection pool slots solely to be rejected. Under projected flash-sale peaks of 5,000 requests, hopeless traffic threatens to completely saturate database connections.
- **Connection pool headroom discipline**: Setting the application connection pool limit (100) equal to PostgreSQL's `max_connections` (100) caused total connection starvation during concurrency bursts, locking out administrative and health check queries (the pool-headroom incident). Application pool sizes must always be capped below server maximums (e.g. `Maximum Pool Size=80`) to reserve operational headroom.
- **Caching must be justified by measurement**: Caching layers should only be introduced when measured database contention and connection saturation prove that the relational database cannot sustainably handle rejection traffic.

## Phase 5: Tiered Architecture (Redis Reservation & Asynchronous Order Fulfillment)
- **Redis as a fast-fail gatekeeper, never the source of truth (ADR-003)**: An atomic Redis Lua script executes stock checks, decrements, and idempotency key recording in a single in-memory round-trip. Rejection traffic never touches PostgreSQL (0 DB hits for rejected buyers), slashing p95 latency from 574 ms down to 29 ms (an 8x performance improvement).
- **Asynchronous order fulfillment protects database write throughput (ADR-004)**: Shifting HTTP semantics to `202 Accepted` with status polling buffers validated orders in a message queue (RabbitMQ / Azure Service Bus). This decouples burst absorption from transactional persistence, allowing background workers to write to PostgreSQL at a sustainable, controlled rate.
- **At-least-once delivery requires consumer idempotency**: In distributed messaging, exactly-once delivery does not exist; exactly-once business effects are achieved through strict idempotency. Enforcing a database unique constraint on `Orders.IdempotencyKey` ensures redelivered messages execute safely as no-ops.
- **Graceful degradation and drift reconciliation**: If Redis becomes unavailable, the API logs a warning and falls back to the synchronous Phase 3 database update (preserving correctness at higher latency). If Redis and PostgreSQL state drift, the worker dead-letters the message with `StockDriftException` and triggers an administrative resync runbook (`POST /internal/resync-stock/{id}`).

## Phase 6: Containerization, Runtime Hardening & Disaster Recovery
- **"A probe that cannot fail is not a probe" (ADR-007)**: Discovered that `await db.Database.CanConnectAsync()` returned `false` without throwing an exception when PostgreSQL was down. A naive probe catching only exceptions returned `200 OK` for an unreachable database. Health probes must explicitly evaluate boolean results and return `503 Service Unavailable` on connection failures.
- **Strict separation of liveness and readiness**: Liveness probes must only verify that the process is responsive; gating liveness on external dependencies causes cascading container restart storms during transient downstream hiccups. Readiness probes gate traffic on required dependencies (PostgreSQL), while resilient/fallback dependencies (Redis, RabbitMQ) do not block readiness.
- **Database migration lifecycle discipline (ADR-006)**: Calling `EnsureCreatedAsync` at startup bypasses the EF Core migrations history table (`__EFMigrationsHistory`), causing collisions (`42P07 relation already exists`) on subsequent migrations. Production applications must use explicit `MigrateAsync` or dedicated migration jobs rather than ad-hoc schema generation.
- **Least-privilege container security and environment compatibility**: Containers must run as unprivileged non-root users (`app`, uid 1654) with minimal writable filesystems. Local orchestration must account for host port conflicts (such as macOS AirPlay/ControlCenter reserving port 5000) using configurable environment mappings (`API_PORT=5065`).
- **Disaster recovery drills must prove data restoration (Phases 3A/3B/3C)**: Backups are theoretical until a restore drill succeeds. Verified database backup and clean-restore procedures using `pg_dump -Fc` with SHA-256 sidecars, offsite Azure Blob Storage with Entra ID RBAC (disabling Shared Key access, ADR-008/ADR-009), and complete recovery of RabbitMQ definitions and Redis cache from PostgreSQL truth.

## Phase 7: Cloud Release Engineering & GitOps
- **Immutable, content-addressed container artifacts (ADR-011)**: Tagging container images with git commit SHAs rather than mutable tags like `latest` ensures 100% traceability from running production pods back to git source code and enables deterministic rollback by reverting commit references.
- **Keyless CI authentication via Workload Identity Federation**: Authenticating GitHub Actions workflows to Azure Container Registry (ACR) using OIDC tokens eliminates static credentials (`ACR_PASSWORD`), removing credential leakage attack vectors.
- **Clean ownership boundaries in GitOps**: CI pipelines build, test, and package container images and commit updated image tags to the Kustomize overlay in Git. ArgoCD in Kubernetes reconciles runtime state from Git. Decoupling image creation from cluster reconciliation prevents manual configuration drift and ad-hoc interventions.
- **Shift-left pre-deployment validation**: Offline validation scripts (`validate-manifests.sh`, `validate-objects.py`, `test-validate-manifests.py` catching 19/19 mutations) verify Kubernetes manifests, resource limits, and namespace references in CI before any interaction with a live Kubernetes cluster.
- **Fail-fast configuration discipline**: Eliminating silent fallbacks (such as falling back to in-memory queues when cloud broker configuration is missing) ensures misconfigurations fail immediately at startup with `MessagingConfigurationException` rather than causing silent data loss in production.
