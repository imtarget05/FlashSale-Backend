## 2. The three narratives

**MAIA** is the complete AI application: a retrieval abstraction that lets one
interface sit over more than one retrieval backend, RAG evaluated separately
from generation so a broken retriever cannot hide behind a fluent answer,
agents with human-in-the-loop approval rather than unattended execution,
streaming responses, the backend controls an AI service actually needs, and a
deployment posture oriented at the cloud rather than at a laptop.

**Enterprise-IT-Helpdesk-Lab** is where I set out to prove that AI can join
enterprise automation without being handed direct privileged execution. The
model may only propose a typed action ID and structured parameters.
Authorization, risk classification, human approval and execution stay
deterministic application code, and the proposal schema has no field for a
shell command at all. The honest boundary is that this is proven by pytest and
by PowerShell AST parsing on this host — live Active Directory mutation is
NOT_RUN, and the gateway is not wired to any HTTP route in the running portal.

**Factory-Data-Automation-v-AI-Reporting-Platform** is where I set out to prove
that AI downstream may only consume data that passed deterministic quality
controls, and that the provenance of what it consumed stays inspectable. A
fail-closed gate authorizes report generation only from validated KPI evidence;
UNKNOWN blocks rather than passes; blocked generation makes zero LLM calls,
asserted at unit and HTTP level. Live on Azure the gate returns GOOD with 5/5
checks and 13 provenance ids — on the GOOD path. The BAD/UNKNOWN branch was
never triggered against the deployment.
