## Atomic flash-sale inventory reservation using a Redis Lua CAS plus a PostgreSQL atomic conditional UPDATE, with a zero-oversell invariant

- **IMPLEMENTATION**: VERIFIED — Two independent gates, and the second one is the one that is actually correct. Gate 1 is a single Redis Lua script (`SCRIPT EVAL`, so check-and-decrement is atomic) that reads `stock:{productId}` hash field `qty`, returns `-3` if the idempotency key is already in the `reservation:{productId}` set, returns `0` if `qty < want`, otherwise does `HINCRBY -want` + `SADD` + `EXPIRE 86400` and returns `1` (`src/FlashSale.Infrastructure/Redis/RedisStockGateway.cs:23-34`, dispatched at `:50-60`). A negative quantity is rejected before the script runs (`:46-47`) so `HINCRBY` can never add stock. Gate 2 is the load-bearing invariant: a single conditional SQL `UPDATE "Products" SET "AvailableStock" = "AvailableStock" - {qty} WHERE "Id" = {id} AND "AvailableStock" >= {qty}` (`src/FlashSale.Infrastructure/Persistence/OrderRepository.cs:30-35`). PostgreSQL decides the winner by row lock; if `affected == 0` the transaction is rolled back and the caller is told stock was insufficient (`:37-41`) — the order is refused, never written. The order insert and the decrement share one transaction (`:28`, `:59-61`), so a persisted order always has a matching decrement. `OrderProcessor` turns a rejected conditional UPDATE into `StockDriftException` rather than retrying (`src/FlashSale.Application/Orders/OrderProcessor.cs:40-46`), and the worker dead-letters drift immediately instead of retrying it (`src/FlashSale.Infrastructure/Messaging/OrderProcessorHost.cs:52-59`). Orchestration: reserve -> enqueue, and release the reservation if the queue is full (`src/FlashSale.Application/Orders/SubmitOrderUseCase.cs:86-134`); if the Redis tier is unavailable the whole thing falls back to synchronous DB processing (`:136-149`). HTTP maps sold-out and stock-drift to 409 (`src/Order.Api/Program.cs:315-326`).

## Asynchronous order processing over RabbitMQ with ack-after-persist, bounded retries and a dead-letter path, made exactly-once by idempotency keys

- **IMPLEMENTATION**: VERIFIED — The API publishes with `BasicPublishAsync(mandatory: true, basicProperties: Persistent = true)` under a `SemaphoreSlim(1,1)` gate that serialises **all** use of the shared `IChannel`, because the client contract is single-threaded per channel and unsynchronised concurrent publishes on one channel were observed to truncate frames mid-string with no exception surfaced (`src/FlashSale.Infrastructure/Messaging/RabbitMQOrderQueue.cs:28`, `:97-117`). Consumption is manual-ack (`BasicConsumeAsync(autoAck: false)`, `:84`) with `BasicQosAsync(0, 10, false)` prefetch (`:62`) into a bounded in-process channel of 100 (`:64`). The body is copied to owned bytes because RabbitMQ.Client v7 only guarantees `ea.Body` inside the handler (`:81-82`, rationale at `:69-80`). The consumer host then does **process-then-ack**: `await processor.ProcessAsync(...)` runs first and `entry.Complete()` (the `BasicAckAsync`) only after it returns successfully (`src/FlashSale.Infrastructure/Messaging/OrderProcessorHost.cs:49-50`) — so a crash before the ack re-delivers rather than losing the order. A transient failure re-queues the message with `Attempt + 1` after exponential backoff and acks the original (`:60-69`); after `OrderProcessor.MaxAttempts = 4` (`src/FlashSale.Application/Orders/OrderProcessor.cs:27`) or on `StockDriftException` it dead-letters via `BasicRejectAsync(requeue: false)` plus a structured `DLQ|...` log line (`OrderProcessorHost.cs:52-59`, `:71-77`, `:81-103`). A malformed delivery is rejected without requeue rather than left unacked forever (`RabbitMQOrderQueue.cs:198-222`). Exactly-once business effect comes from the idempotency key: the processor short-circuits if the key already produced an order (`OrderProcessor.cs:32-38`) and the database enforces a unique index on `Orders.IdempotencyKey` (`src/FlashSale.Infrastructure/Persistence/AppDbContext.cs:46`).

## Checkout saga with durable state, bounded payment retry and automated compensating transactions

- **IMPLEMENTATION**: VERIFIED — `CheckoutSagaCoordinator.ExecuteSagaAsync` is an orchestrated saga over three ports. It opens by checking the idempotency key and returning the stored terminal result rather than re-running (`:48-73`; a completed saga returns its original `SagaId`/`OrderId`). It persists a `CheckoutSagaState` row at `Started` (`:76-89`) and publishes `CheckoutSagaStartedEvent` through a `PublishSafeAsync` wrapper that swallows and logs publish failures so a bus outage cannot lose the saga (`:91-101`, `:264-274`). Step 1 reserves inventory; any result other than `Reserved`/`Duplicate` is a fast fail with no payment call and no compensation needed (`:104-117`). Step 2 persists the order through the atomic conditional UPDATE, and if that fails it **releases the Redis reservation before returning** — the drift compensation (`:129-142`). Step 3 retries payment at most `maxAttempts = 2` and only on a transient error, with a linear `50 * attempt` ms delay (`:157-176`). On success it marks paid and publishes `CheckoutSagaCompletedEvent` + `OrderConfirmedEvent` (`:179-213`). On decline/timeout it transitions to `Compensating`, then runs **two** compensations: release the Redis reservation (`:226`) and cancel the order plus restore DB stock (`:231`), ending at `Compensated` and publishing `CheckoutSagaCompensatedEvent` + `OrderCancelledEvent` (`:234-254`). Surfaced as `POST /api/saga/checkout` returning 200 / 422 / 400 (`src/Order.Api/Program.cs:499-533`).

## Password hashing with PBKDF2-HMAC-SHA256, JWT auth with refresh-token rotation and replay protection, and account-enumeration resistance on auth endpoints

- **IMPLEMENTATION**: VERIFIED — Hashing: `Pbkdf2PasswordHasher` derives with `Rfc2898DeriveBytes.Pbkdf2(..., HashAlgorithmName.SHA256, 32)` at `DefaultIterations = 210_000` with a 32-byte `RandomNumberGenerator` salt, and stores a self-describing `pbkdf2-sha256$iterations$salt$hash` string so the work factor can be raised without a flag day (`src/FlashSale.Infrastructure/Auth/Pbkdf2PasswordHasher.cs:21-46`). Verification parses that same format and compares with `CryptographicOperations.FixedTimeEquals` (`:48-74`), returning `false` for malformed/foreign-format input rather than throwing. JWTs: HS256 with issuer, audience, lifetime and `ValidAlgorithms = [HmacSha256]` validation (`src/FlashSale.Infrastructure/Auth/JwtTokenIssuer.cs:97-123`); access token 15 minutes, refresh 7 days (`:31-32`). Both token types are signed by the same key but carry a `typ` claim, and `ValidateRefreshToken` rejects anything whose `typ != "refresh"` — that is what stops an access token from being rotated forever (`:29`, `:63`, `:92`). Rotation carries a `ver` claim holding the user's `TokenVersion` generation (`:26`, `:93`). Replay protection is a **single conditional SQL statement**, not read-validate-write: `UPDATE "Users" SET "TokenVersion" = "TokenVersion" + 1 WHERE "Id" = @id AND "TokenVersion" = @presented` — rows affected is 1 for the winner and 0 for a replay, so of two concurrent refreshes exactly one can succeed (`src/FlashSale.Infrastructure/Persistence/UserStore.cs:47-60`; the same store lets the unique `Users.Email` index arbitrate duplicate registration rather than a racing pre-flight SELECT, `:28-45`). Enumeration resistance: `LoginAsync` returns one identical `AuthError.InvalidCredentials` / "Invalid email or password." for both an unknown email and a wrong password (`src/FlashSale.Application/Auth/AuthService.cs:59-63`), and the endpoint never returns 404 for a missing account (`src/Order.Api/Auth/AuthEndpoints.cs:114-123`). Duplicate registration *does* return 409 by design (`AuthEndpoints.cs:120`) — that is intentional, because the caller is a registration form; the enumeration defence is on **login**, not register.

## Known Security Issues (must fix before showcasing)

Neither of these belongs on a CV. Both are verified findings, listed so you are not caught out if a reviewer runs the app.

1. **Hard-coded STAFF account seeded into every database at startup.**
   `src/FlashSale.Infrastructure/Persistence/DatabaseInitializer.cs:60-80`. `InitializeAsync` upserts a user with email `staff@flashsale.local`, `Role = AuthRoles.Staff`, `Id = 00000000-0000-0000-0000-000000000001`, `TokenVersion = 0`, and a **password literal hard-coded in the repository** at `DatabaseInitializer.cs:69` and again at `:77`. It is not guarded by any environment check — `DatabaseInitializer.InitializeAsync` is called unconditionally by the API at `src/Order.Api/Program.cs:223`, so this privileged account is created in Development, in the Testcontainers integration tests, and in any environment where the API boots. The literal itself is a known, published, guessable credential in a public repository, so treat it as compromised. (The hashing is fine — the literal is hashed with PBKDF2 at 210k iterations on every boot — but the password is still in the source.) Fix: gate the seed behind an explicit opt-in flag or remove it from non-Development environments, and source the credential from configuration/secret storage instead of a literal.

2. **Unauthenticated state-mutating endpoints.** Authentication *is* registered (`src/Order.Api/Program.cs:174-194`) and JWT bearer validation is configured, but almost none of the mutating surface is gated by it. In `src/Order.Api/Program.cs`, these are `POST` handlers with no `.RequireAuthorization()`:
   - `POST /api/orders` — creates orders and decrements real inventory (`:277-351`). The code comments this as deliberate (`:293-296`, "deliberately NOT [Authorize]") because the concurrency evidence depends on the anonymous path — but that means anyone unauthenticated can buy stock.
   - `POST /api/orders/{idempotencyKey}/pay` — transitions order state (`:368-396`).
   - `POST /internal/resync-stock/{id}` — overwrites the Redis stock mirror for any product (`:488-494`). Reachable by anyone, and it directly influences what the reservation gate will accept.
   - `POST /internal/automation/payment-timeout-scan` (`:400-409`), `POST /internal/automation/low-stock-scan` (`:413-428`), `POST /internal/automation/daily-report` (`:432-450`) — all write `AutomationRun` audit rows and can cancel orders and release stock.
   - `POST /api/saga/checkout` — runs the full checkout saga, including payment and compensation (`:499-533`).
   - `POST /api/outbox/enqueue` (`:547-562`), `POST /api/outbox/requeue` (`:593-599`), `POST /api/inbox/consume` (`:601-614`) — enqueue, revive and deduplicate-poke the outbox/inbox.
   - The read endpoints `GET /internal/metrics`, `GET /internal/automation/summary`, `GET /internal/automation/alerts`, `GET /api/outbox/pending`, `GET /api/outbox/stuck` (`:243`, `:252`, `:261`, `:567`, `:576`) are likewise open and leak operational and business data.
   - The **only** endpoint in this file with `.RequireAuthorization()` is `GET /orders/me` (`:474`); `/api/auth/logout` and `/api/auth/me` are also protected (`src/Order.Api/Auth/AuthEndpoints.cs:62`, `:74`). A role policy exists (`src/Order.Api/Auth/AuthPolicies.cs`, registered at `Program.cs:194`) but is applied to none of the endpoints above.
   Fix before showcasing: require authorization on every mutating and every `/internal/*` endpoint, apply the STAFF policy to the automation and outbox routes, and gate anonymous ordering behind an explicit feature flag so the concurrency harness can still opt in.
